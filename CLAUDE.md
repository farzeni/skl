# skl

skl is a CLI for agent skills: Claude Code first, and opencode, pi, Codex and the other agents that read the same skill folders. It keeps your skills in one git repo (the vault), loads any mix of them on any machine, can roll back any change, and lets a skill **learn** from another one: copied as is if you don't have it, or through an LLM interview if you do. `learn` is the only way a skill from elsewhere gets in.

**Status: v0.1 built, going public (user, 2026-11-11).** Merged packages: `cli`, `ui`, `config`, `gitx`, `errs`, `selector`, `resolve`, `state`, `ref` (repo forms only), `vault`, `load`, `app`. Merged commands: `init` with the import offer (#91, #118), `use`/`add`/`drop` in the user scope (#104), `status` and `--json` (#108), `save` (#112), `history` and `--json` (#111), save-back of edits (#113), `rollback [N]` (#116), `import` (#118), `sync` with conflicts by hand, `--continue`, `--abort` (#117, #123), the `claude` and `agents` targets, `help` and `--version`. Not built: `learn` (v0.2, v0.3), `open`, project scope and `completion` (v0.4), the third-party parts. `docs/design/roadmap.md` "What works in v0.1" is the public list; pages keep their "Design preview" warning until everything on them is built. The binary in `demo/bin/skl` is a scripted mock that exists only for the demo recording.

## How we work

Documentation-driven development: the docs in `docs/` are the spec. Every behavior is written there first, from the user's side, and every claim is proven before any code is written. If an experiment contradicts the docs, the docs change. If something gets built that the docs don't describe, it gets documented first.

Every change goes through the project skills, in order. Each one picks up the state the previous one left:

| Skill | Starts from | Leaves |
|---|---|---|
| `/skl-investigate` | a question or a doc claim | a closed investigation in `.workbench/` with findings, decisions and a plan |
| `/skl-implement` | a closed investigation, or a code card | a card In Progress, a worktree, a change verified with `/testit`, an open PR |
| `/skl-validate` | a code card's open PR | GREEN on the PR head, or numbered findings, with proofs (code cards only) |
| `/skl-merge` | a PR the user approved, or a code card's PR with GREEN | the PR merged, the card Done, the worktree removed, the investigation delivered |

Never commit to `main` directly.

**Building the code (user, 2026-10-25).** A **code card** is an issue with a `sprint-N` label whose body has `Docs implemented` and `Acceptance` sections. The card and the doc pages it names replace the investigation.
- The coordinator session (SKL) moves cards from Backlog to Todo and starts one implementer agent per card, at most 3 cards at a time.
- The implementer works the card with `/skl-implement`: spec scripts first, then code, `make check` and `/testit`, then an open PR.
- A separate validator agent checks the PR with `/skl-validate`, against the card and the docs, on the PR head, with proofs. It answers GREEN or numbered findings. The two iterate until GREEN. After 3 rounds without GREEN, the coordinator steps in.
- On GREEN, with CI green, the implementer merges with `/skl-merge`. Code cards need no "merge" from the user. GREEN also covers the doc edits a code card names, unless they change a doc's meaning. Docs PRs (docs mode) still wait for the user's "merge".
- A doc found wrong or silent, a change to a doc's meaning, or a change to a decision here goes to the user through the coordinator, and a docs PR comes first.

## Stub tests

Stub tests (spec tests) turn doc statements into executable checks before the code exists. They are black-box: they run `skl` against a temporary `HOME` with local bare git repos standing in for GitHub, and assert on exit codes, output and files on disk. Each test names the doc sentence it checks.

- They are [testscript](https://pkg.go.dev/github.com/rogpeppe/go-internal/testscript) scripts, one txtar file per doc page or section: `spec/testdata/<page>[-<section>].txtar` (`skill-sets-status.txtar` ↔ `docs/guide/skill-sets.md` "What's loaded").
- The first line names the page (`# docs/guide/skill-sets.md`). Each block is preceded by the sentence it checks: `# "<doc sentence>"`.
- `skl` runs in-process. `spec/spec_test.go` uses `testscript.Main`, so the test binary acts as `skl` through the real `main` path, and coverage counts (`make cover`).
- Each script gets `HOME=$WORK/home`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=$HOME/.gitconfig`, `COLUMNS=80`, and a `.gitconfig` that maps `https://github.com/` to local bare repos under `$REMOTES`, so skl needs no test hook.
- Helper commands live in `spec/spec_test.go`; add one when a script needs it. `remote <owner/repo> [dir]` creates a bare repo, seeded from `dir` if given. `exitcode <n> <program> [args…]` runs like `exec` and checks the exact exit code (`! exec` only checks non-zero). `spec/testdata/harness/` tests the harness itself.
- Expected output is golden (`cmp stderr want.txt`). `make golden` (`UPDATE=1 go test ./...`) rewrites it, in spec scripts and in package `testdata/*.golden` alike. Review the diff.
- Each code card writes the scripts for the doc sentences it implements. Put `skip 'pending: <page>'` at the top of a script only for a sentence the card leaves for later.
- Pure logic with a clear contract (selector parsing, resolution order, config precedence) also gets table tests in its package.

## Decisions already made

Don't reopen these without a reason from an experiment.

- Name `skl`. The combine concept is `learn`; one run is a **lesson** (`[[lesson]]` in `.skl-origin.toml`).
- Default scope is user (`~/.claude/skills`); `--scope project` for `./.claude/skills`.
- Every change creates a **generation**; `skl rollback` never rewrites git history.
- Git is the only backend; no server. One Go binary that shells out to the git CLI.
- `learn` runs the engine (the user's `claude` CLI by default) in a prepared workspace. The engine writes to staging; only skl commits.
- `skl learn <peer> [skill] ["<text>"]` (reverses PR #10; there is no `skl fork`). The skill a lesson learns from is its **peer**. No flags for the target or a focus; the optional text goes to Claude as is. One peer per run. The last argument is text if it contains whitespace. The target is `name`, `group/name` or `group/`; left out, it's the vault skill with the peer's name. Names match a folder or frontmatter `name`; a name in two groups stops and asks for `group/name`.
- Target exists → lesson. Missing, no text → verbatim copy, no Claude, recorded as `[source]` (`url`, `commit`, `tree`, `ref` if pinned, `license`) in `.skl-origin.toml`; a renamed copy gets its frontmatter `name` rewritten. Missing, with text → a lesson into an empty skill, recorded as `[[lesson]]` only (no `[source]`). A new skill's default group is the peer's owner (`someone/agent-skills/pdf` → `someone/pdf`), or a local repo's folder name; a repo-root skill (`someone/pdf-skill//`) takes its frontmatter `name`, else the repo name. skl prints `→ copy into …`, `→ lesson into …` or `→ new skill …`; `skl rollback` is the undo. A learned new skill is loaded in the same generation.
- **Reversed by the user (2026-10-22, #29):** PR #22's "never asks for confirmation". Before someone else's new skill, or an update that changes their scripts (any changed non-`*.md` file or mode) or raises a license issue, skl shows the description, license and scripts and asks `Add it?` once; `--yes` answers. **Dropped (coordinator, #29):** `--as` (the landing prompt keeps "save as") and `--all`.
- `skl learn <someone>/@set [@name]` copies their set and every skill it names into the owner group (`someone/…`); the set file lists the copies, and `sets/<name>.origin.toml` holds `[source]` and `selected`, the lines skl last wrote (review C11f, 2026-10-22). Two of their skills with the same folder name: the later lands as `<group>-<name>` with its frontmatter `name` rewritten, printed. A vault skill at the target that isn't a copy of theirs is skipped with a warning, never a lesson. Learning it again copies new skills, updates each one, drops removed ones from the set file (the vault copies stay) and keeps your own lines. Never a lesson. (Replaces "rewritten to their repo", #29.)
- `skl learn <skill> ["<text>"]` with only your skill takes changes from the last lesson's peer, or a copy's source. skl picks the path from `tree` (their folder at `commit` as landed): their tree didn't change → up to date; your folder equals `tree` → update, the folder replaced, no Claude; otherwise, or with any text → a lesson over base, peer and mine, with `git merge-tree`'s result as a starting point. An edited skill always updates by lesson, even if the text merge is clean; without the `claude` CLI it stops. After a lesson, `tree` becomes theirs at the new commit. "Take theirs" has no flag: say it in the text. `skl learn` with no arguments takes every update; `--dry-run` lists. **Removed by the user (#29):** `skl upstream`, `--merge`, `upstream --continue`. `skl sync` checks sources (never applies); `skl status` shows `update available` offline.
- Tags and commits pinned with `#` never update; branches are followed.
- Licenses (user, #29; a docs design, not legal advice): the vault has its own `LICENSE`, written by `skl init` from config `license` (default MIT). skl finds a skill's license (folder, repo root, frontmatter) and copies a root license into the copy. No license, an unknown one, or a non-permissive one that isn't the vault's is an issue: skl asks (keep their license and notice / no / as it is), or Claude asks in a lesson. No other rule. **Details (user, 2026-11-12, #140; `docs/guide/learn.md` "Licenses"):** permissive = exactly MIT, MIT-0, 0BSD, BSD-2-Clause, BSD-3-Clause, Apache-2.0, ISC, Zlib, BSL-1.0, Unlicense, CC0-1.0. Frontmatter `license` counts only as an SPDX id or expression, only when folder and repo root have no license file (free text ignored); then no notice file, printed `MIT (from SKILL.md, no license file)`. Several `LICENSE*`/`COPYING*` at the first level found → all read, one SPDX expression (`MIT OR Apache-2.0`), an issue only if no alternative is permissive or the vault's, all copied with a root license. The vault's license is its `LICENSE` file (same detector), else config `license`; with no file (`none`) every non-permissive license is an issue.
- skl never changes or removes skills it didn't create.
- Any git remote works for every command that takes a repo. `owner/repo` means the default host (GitHub); `//` separates a repo from a path inside it; `#` pins a ref. See `docs/reference/repos.md`. **Details (user, 2026-11-12, #140):** a host form without `//` is all repo (GitLab subgroups); unreachable with 3+ parts after the host, the error hints `if pdf is a folder in the repo: skl learn gitlab.com/team/skills//pdf`. The first `#` after repo and path starts the pin, the rest is the ref name (`pdf#v1#rc`). A skill set can be pinned (`…/@backend#v1.2`): the set and every copy record the pin (`ref`, `ref_kind` in `sets/<name>.origin.toml`). `skl init you/skills#dev` is a usage error. `repo//sub/@backend` reads `sub/sets/backend.toml`, selectors resolve under `sub/`. A local source is stored with `~` under HOME, else absolute; on a machine without it the update check warns `! someone/pdf: ~/code/skills isn't on this machine · skl sync on the machine that has it`. Cache: `cache/<host>[_<port>]/<path>` (user dropped), `cache/local/<absolute path>`, one clone per repo with a growing sparse set. A lesson's merge base comes from the vault's history, never fetched.
- Per-machine settings live in `~/.skl/config.toml`, edited by hand (no `skl config` command); the file is optional. Precedence: flag, env var, file, default. There is no `vault` key: the vault is the clone at `~/.skl/vault` and its `origin` (review C8). Env vars beyond `SKL_<KEY>`: `SKL_HOME`, `SKL_DEBUG`, `NO_COLOR`, `BROWSER`.
- A **skill set** is a list of selectors (no "profile", no "loaded set"). The loaded one is the **active skill set**; `skl save <name>` stores it as a **named skill set** in `sets/<name>.toml`, one selector per line, loaded with `@name`. It stores selectors, not a resolved list. `save` creates or overwrites (asks first); edit or delete the file by hand. No set subcommands. `sets`, `lessons` and `h` can't be group names. "skill set" in prose, "Skill sets" in titles.
- A skill set in someone else's repo is `<repo>/@name` (an `@` at the start of the last path part; `<repo>@name` collides with SSH URLs), as a `learn` argument only. Rollback stays global: a generation is a snapshot of the active skill set; there is no `skl rollback @set`.
- Two parts (`review/pr-review`) is your vault; three or more, a host, a URL or a local path is a remote; `//` separates a nested path. **Reversed by the user (#29):** selectors are vault-only; `use`/`add`/`drop` reject a typed remote reference with a hint to `skl learn` it. A set line naming one stops with `✗ @hasref: someone/agent-skills/pdf is someone else's skill · edit sets/hasref.toml`, exit 1 (user, 2026-11-02). There are no read-only remote skills. Grammar corners (review C14, `docs/reference/repos.md` "Grammar"): `-` removes groups and sets too (`-review`, `-@base`); names have no dots; an owner name that's reserved or invalid gets the group `<owner>-skills`; a one-word name that's a skill but no group warns `! pdf   matches no group · skl use someone/pdf`. Sources and peers are stored as canonical URLs: HTTPS for shorthand, as typed otherwise, trailing `.git` dropped.
- skl's flags are `--long` only and can go anywhere, as `--x v` or `--x=v`; `--` ends flags. Every other word is a selector, so `-review/test-gaps` is a removal (Go's stdlib `flag` can't parse this; skl parses its own args). **The one exception (user, 2026-10-22, D1):** `-h` always means `--help`. Help is `skl help [cmd]`, `--help`/`-h`, and bare `skl` lists the commands; `skl --version` prints the version and build commit.
- Vault-changing commands commit locally and never push (user, #31: no auto-push); `skl status` and a `! N changes not pushed · skl sync` line before the `✓` remind instead. `skl sync` commits hand edits, merges (never rebases), pushes, and reloads the loaded selectors. A conflict is resolved with Claude (learn engine), by hand (`--continue`), or aborted.
- A skill whose name (folder or frontmatter `name`) is taken by a skill skl didn't create is skipped with a warning. `skl import <name>… [--group <g>]` copies such skills into the vault; the group defaults to the vault's owner (`you/skills` → `you/`). An imported skill joins the active skill set, as `skl add` would. `skl init <repo> [selectors]` clones or creates the vault, loads the selectors, and offers to import the skills in `~/.claude/skills` that aren't in a vault (#31).
- Loaded skills are copies, not links. Each holds `.skl-copy.toml` (source, always a vault skill; commit; `tree`, the folder's git tree hash), which is never saved back. Changes to a copy are saved back to the vault (three-way with `git merge-tree`, base = the recorded commit; review X1, X2) at the start of every command that changes something, as their own generation. People make and improve skills in Claude Code; there is no `skl new`, and `skl import` adopts the folder as skl's copy.
- Hand edits in the vault are committed as their own generation before any vault-changing command, except while a sync merge is open: then they go into the merge commit at `skl sync --continue` (git can't commit mid-merge; user, 2026-11-11). A selector that matches nothing warns and is listed in `skl status`.
- A remote reference whose path has no `SKILL.md` and is one word names a skill: skl looks it up in the repo by folder or frontmatter `name` and records the path it found. Two matches stop and list the paths. So `someone/agent-skills/pdf` works although the folder is `skills/pdf`. The lookup follows the vault's name rules (case and Unicode form folded, exact folder name wins, hidden and out-of-grammar names skipped, any depth; user, 2026-11-12, #140).
- `skl open [ref]` replaces `skl star` (no bookmarks, no `stars.toml`). It always prints the web URL of a vault skill, skill set, remote ref or repo, and opens a browser only when stdout is a terminal and a screen exists (no flags; a failed launch exits 0). Known hosts: GitHub, GitLab, Bitbucket, Gitea/Forgejo, sourcehut, Azure; a `[web]` table in `config.toml` names a self-hosted server's software; otherwise the repo root. A copied skill opens its vault page and prints its source. A local repo prints its path. A two-part argument is a vault skill if one exists, else `owner/repo` on the default host (review X6). Core, not third party.
- One output vocabulary (#31, listed in `docs/reference/commands.md` "Output"): `→` plan, `◇` step, `+ ~ −` loaded/replaced/unloaded, `?`/`›` question (first answer is the default), `!` warning, `✗` error, `✓` result, last; a change ends `✓ generation N · skl rollback to undo`. Every `!` and `✗` line ends with the command to run, after `·`, on the next line if it doesn't fit. In user-facing prose, a skill in `~/.claude/skills` is "loaded", not a "copy"; "copy" is a skill learned without Claude.
- Anything that depends on a third-party service or file format is a removable part: code in `thirdparty/<name>/` behind `internal/ext` (commands, reference rewriters, import sources), docs in `docs/thirdparty/`. Core code and core docs never assume a part exists; core pages only link to it. The parts are skills.sh (`skl search` on its undocumented `/api/search`, skills.sh links as references) and npx skills (`skl import` reads `~/.agents/.skill-lock.json` v3 for the source). skl never creates remote repos; init needs an existing repo (user, 2026-10-24, reverses D4, which had a gh part), and one it can't reach stops with `✗ can't reach you/skills · create it or check access, then skl init you/skills`, since hosts answer "not found" for a missing repo and a private one alike. `protocol` defaults to `https`. skl sends no telemetry and never checks for its own updates.
- **CLI conventions (docs review, user, 2026-10-22; `docs/reference/commands.md`).**
  - Exit codes: `0` done (warnings, a no-op and `--dry-run` included), `1` error, `2` usage error, `130` Ctrl-C. A warning never changes the exit code; a skipped skill is a warning.
  - Questions: `--yes` takes the first answer of every question. Without a terminal and without `--yes`, a question stops the command before it changes anything. A lesson and a sync conflict resolved with Claude always need a terminal: `learn` stops before Claude runs, `sync` undoes the merge and stops. One exception to "first answer is the default": `skl save` overwriting a set with one that would remove every line defaults to `no`; `--yes` still means yes, and an empty set stays valid (user, 2026-11-11).
  - Output: what you asked for (status, history, the `open` URL, a `--dry-run` plan, `--json`) on stdout; marks and questions on stderr. Color only on a terminal; `NO_COLOR` and `TERM=dumb` turn it off.
  - **D2 (user):** `--json` on `status` and `history` only (format may change until 1.0); `SKL_DEBUG=1` prints each git and engine command to stderr, plus skl's internal diagnostics, such as a state file problem it works around (user, 2026-11-01). **D3 (user):** `skl completion bash|zsh|fish` completes commands, flags and vault selectors (roadmap v0.4).
  - `--dry-run` works on every command that changes something and prints the plan, starting with the save-back a real run does first (`→ save pr-review → review/pr-review`, `→ commit …` for vault hand edits; user, 2026-11-11); `sync --dry-run` fetches but doesn't merge or push. `--scope` applies to `init use add drop save learn` (and `import`; not `rollback`, #53); `project` is `.claude/skills` at the git repo root, an error outside a repo.
  - Generations: a command that first saves edits makes two generations (the save, then its own); a no-op makes none and ends `✓ nothing to change`. A generation is made whenever the active skill set changes, even if no skill folder does (a reorder, dropping a line that matches nothing), so rollback restores it (user, 2026-11-02). Generations are local, numbered per machine. A project scope's active skill set lives in `state.json`, keyed by the repo's top-level path (so per machine, and a git worktree is a repo of its own). Loading, unloading and sync's reload act on the user scope and the current repo's project scope only. **Reversed by the user (2026-10-25, #53):** rollback restores every scope the undone generations changed, in any repo (a repo that's gone is skipped); `skl history` shows the repo a generation ran in (`use @frontend · ~/code/prj1`).
  - Safety: one skl runs at a time (a lock). While a by-hand sync merge is pending, only `status`, `history`, `open`, `help` and `sync --continue|--abort` run. Ctrl-C at a question takes the answer that changes nothing, usually the last (user, 2026-11-15, #135: `skl save`'s empty overwrite takes `no`); Ctrl-C while changing finishes or undoes the current step.
- **Learn and import details (docs review, coordinator calls accepted by the user, 2026-10-22).** A learned new skill joins the active skill set, as `skl add` would. "Scripts" = any non-`*.md` file. `Land it` for a lesson is `› replace  change it  save as …  discard`; a discarded lesson records nothing. Your own vault skill is never copied (`✗ … already in your vault`, with a hint to run a lesson). `skl import` replaces a symlink in `~/.claude/skills` with a real copy, and runs the license check when an import source part finds where the skill came from. How lessons run Claude (Claude Code's own interview UI vs skl asking) is proved by a spike before v0.3.
- **Other agents (user, 2026-10-22, #47).** skl loads skills for every agent that reads Agent Skills folders, through **targets**: config `targets = ["claude"]` (default; `SKL_TARGETS`, comma-separated) can add `"agents"`. `claude` = `~/.claude/skills` / `.claude/skills`, `agents` = `~/.agents/skills` / `.agents/skills`; no per-agent folders or agent names. Each target holds its own copy with its own `.skl-copy.toml`, saved back three-way like copies on two machines. `status`, the didn't-create check and `import`/`init` scan every target's folders; `status` also warns about a same-name skill skl didn't create in `~/.agents/skills` even without that target, since opencode reads it first. The "Which agents read them" table lives once, in `docs/guide/skill-sets.md`. Lessons and sync conflicts run through an **engine**: config `engine` (`SKL_ENGINE`) replaces the `claude` key, no alias. Contract: skl prepares the workspace with the bundled skill at `.claude/skills/<skill>/` and `.agents/skills/<skill>/`; starts the engine there on the user's terminal with one first prompt; the engine uses its own login, interviews and writes only `result/`; a non-zero exit or empty `result/` lands nothing. **Generic engine (user, 2026-10-24, via SKL; replaces opencode/pi engine parts):** `engine = "claude"` (default, core) runs `claude "<prompt>"`; any other value is a command template run in the workspace under the same contract, e.g. `opencode --prompt {prompt}`, `pi --skill {skill} {prompt}`. Placeholders `{prompt}` (first prompt) and `{skill}` (bundled skill's path in the workspace). skl splits the template into words itself (spaces; double quotes group), no shell, each placeholder one argument even inside a word; string form only. An unknown placeholder, unclosed quote or command not on `PATH` stops the lesson before it starts with `✗ engine: … · edit engine in ~/.skl/config.toml`. No engine parts and no `RegisterEngine` hook; the recipes live once, in `docs/guide/learn.md` "Other agents". Wording: "Your agent skills, in one repo, on every machine"; Claude Code is named first and stays the worked example.
- **Project scope (#53, 2026-10-25; D1, D2, D6, D7 the user's, D3, D4, D5, D8 coordinator calls).** Each repo has its own active skill set next to the user scope's; the worked example is `@reviews` (user), `@frontend` in prj1, `@backend` in prj2, in `docs/guide/skill-sets.md` "For one repo only". **D1:** skl doesn't touch the repo's git (no `.git/info/exclude`, no `.gitignore`); the docs say loaded copies are untracked, name the `git add -A` trap and give the exclude/`.gitignore` tip, once, in that section. **D2:** a folder git tracks is never skl's, even with a committed `.skl-copy.toml`: `skl status` doesn't list it, a same-name loaded skill is skipped (`! team-style   skipped: .claude/skills/team-style is committed in this repo · skl drop frontend/team-style --scope project`), and `skl import --scope project` refuses with `✗ team-style is committed in this repo · skl learn team/prj1/team-style`. **D3:** `skl init --scope project` also offers the repo's untracked skills; otherwise `skl status` lists them with `skl import <name> --scope project`. **D4:** a project import's default group stays the vault owner's. **D5:** `skl save <name>` saves the given scope's active skill set; a self-reference (`@name` in the set saved as `name`) is replaced by that set's own lines; later `add`/`drop` change the active skill set, not the file. **D6:** save-back reads every copy recorded in `state.json`, in every repo; a repo whose copies are behind the vault shows `vault changed · skl sync` in its `skl status`; a repo that no longer exists is forgotten.
- **Building skl (2026-10-25; the user's unless marked as a coordinator call).**
  - Go module `github.com/farzeni/skl`. skl itself is MIT. CI runs on Linux and macOS (`ubuntu-latest`, `macos-latest`). One card = one PR. Spec tests use testscript.
  - skl needs git 2.38 or later (D3). Save-back merges with `git merge-tree --write-tree` and a synthetic commit instead of `--merge-base`, which needs 2.40, so macOS's git 2.39 works. `gitx` stops with `✗ skl needs git 2.38 or later (found X) · update git`.
  - Spec tests run `skl` in-process (D1, coordinator call). Spec scripts are written per card, not all at once (D2, coordinator call).
  - Dev tools are pinned in a separate `tools/go.mod` and run through `make` as `go tool -modfile=tools/go.mod <tool>`, so the main `go.mod` stays small (D4, coordinator call).
  - Conventions (architecture, errors, context, output, testing layers) live in `CONTRIBUTING.md`.

## Confirmed assumptions

- Claude Code notices new or changed skill folders in `~/.claude/skills` and the project `.claude/skills` during a running session, except a top-level skills folder created after the session started, which needs `/reload-skills` (so a repo's first `--scope project` load may need it). From the Claude Code skills docs, "Edit a skill during a session", read 2026-10-25 (#53).

- opencode 1.19.4 reads `~/.claude/skills` and `./.claude/skills` by default, nested and linked folders included, and a skill in `~/.agents/skills` wins over them. pi 1.4.0 (`@earendil-works/pi-coding-agent`) reads `~/.agents/skills` and `.agents/skills`, not `~/.claude/skills` unless its `settings.json` has `"skills": ["~/.claude/skills"]`. Neither sees changes in a running session (restart, `/reload`). Tested in a throwaway HOME, 2026-10-22 (#47).

- `git merge-file` merges `SKILL.md` edits cleanly only when they are at least a line apart, and a clean merge can still contradict itself; a folder modify/delete needs `git merge-tree` (#29). So merges only feed a lesson, and save-back merges a folder with `git merge-tree` (docs review X1, 2026-10-22).
- A recorded git tree hash tells exactly whether a copy is unchanged (edits, undone edits, mode bits, CRLF), offline, in a few ms (#29).

- Claude Code loads skills from symlinked folders in `~/.claude/skills` and `.claude/skills`, and reads `SKILL.md` from the target (Claude Code skills docs, 2026-10-21). Issue #7. skl now loads copies, not links (issue #15), so this no longer matters.
- Fetching one skill folder with `git clone --depth 1 --filter=blob:none --sparse` works on GitHub, GitLab, Bitbucket, Gitea, Forgejo and local `file://` repos, and older commits can be fetched by sha on demand. Issue #1.
- The vault layout works as an `npx skills` source without extra files (skills@1.7.4, through its recursive fallback; `sets/` and `lessons/` are ignored). Issue #20.

## Writing the docs

- Perfection is reached by removing what isn't essential. Before adding a page, section, flag or command, check whether an existing one already covers it. Say each thing once and link to it elsewhere.
- Write from the user's side: what they type, what they see, what changes on disk.
- Use generic examples only: vault `you/skills`, groups like `review`, `data`, `writing`, peer `someone/agent-skills/...`. Never the maintainer's own projects, names or tools.
- Plain, direct sentences. No marketing tone.
- Order pages and sections by value to the user: what they get first, daily use next, edge cases and mechanism last. Every guide page opens with its goal in one sentence.
- Every page about planned behavior keeps the "Design preview" warning until the feature ships.
- When you change commands or output, update `demo/bin/skl` and `demo/demo.tape` so the recording stays true to the docs.
